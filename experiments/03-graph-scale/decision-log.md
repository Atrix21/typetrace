# Experiment 3: decision log

Format: **ID** · decision · reason · alternatives rejected. Experiments 1 and 2 are immutable reference points; nothing here changes their data, configs or conclusions.

- **E3-D01** · Repository discovery (2026-11-09): candidate repositories were assessed for size, language and framework; the ladder below was chosen (details withheld: they concern unrelated private repositories).
- **E3-D02** · Smaller candidate repositories (under 11k lines, with little or no bug history) were rejected as scale targets: the experiment-1 repository (6,268 non-test TypeScript lines) had already proved too easy, so the ladder moves up in size, within one language and framework family. No extractor for another language was built for this experiment.
- **E3-D03** · Hold language and framework constant; climb a ×10 size ladder of real TypeScript/NestJS backends: **S** = nestjs-boilerplate (6.3k non-test lines, experiment 1), **M** = Immich server (62.6k), **L** = Twenty server (763k). · The existing TypeScript-Compiler-API extractor, chunkers, retrieval methods, MCP server and agent harness work unchanged, so effort goes into tasks and measurement. Holding language and framework constant removes a confound that a Go or mixed-language ladder would add. · Rejected: Go repositories (would need a new extractor and add a language confound); one very large repository only (no scale gradient).
- **E3-D04** · Snapshots: sparse, depth-1 clones pinned by commit (`immich-app/immich` a203e288, `server/`; `twentyhq/twenty` bde4ff13, `packages/twenty-server/`) in `targets/exp3/` (git-ignored). Immich server dependencies installed with `pnpm install --ignore-scripts --filter ./server` (lifecycle scripts not run). Twenty dependencies not installed yet (12% of call sites unresolved without them).
- **E3-D05** · Scale fix to shared graph code: `graphHash` and `exportGraphJson` now stream element by element. Twenty's canonical graph JSON exceeds V8's maximum string length (`RangeError: Invalid string length`); extraction itself had finished (71 s, 4.4 GB). Output bytes are identical to the old implementations: a new test compares both on fixtures and re-derives the recorded experiment-1 base-graph hash. · Needed for any repository above ~5k files; changes no result of experiments 1–2.
- **E3-D06** · Complexity profile is computed from the graph by `scripts/exp3/graph_profile.py`: separate measured quantities, no composite score. Module boundaries are measured three ways (first directory, first two directories, Louvain communities on the file dependency graph). · Directory-based modules mean different things in feature-organised (nestjs-boilerplate) and layer-organised (Immich: controllers/, services/, repositories/) code; a community partition is architecture-agnostic. A single "complexity score" would hide which property matters.
- **E3-D07** · Compact agent-facing context prototype (`src/retrieval/compact-context.ts`) measured on experiment 1's frozen test runs (no model calls; `results/compact-prototype.json`). Pointer-style output (location, signature, nearest neighbours; no bodies) at ≤ 800 tokens kept 72% of relevant symbols vs 85% for hybrid's 6.3k-token native context. **At equal token cost, adding relationship lines did not beat listing more ranked symbols** (hybrid 0.70 with relations vs 0.72 without; similar for custom_graph; relations helped the weaker BM25/embeddings rankers at ~400 tokens). · Hence the protocol compares graph and no-graph compact tools at equal token budgets, never "graph tool vs baseline" alone.
- **E3-D08** · Ground truth is never produced by the retrieval systems under test. Sources: fix commits of merged PRs (functions changed), linked issue text as the query (verbatim), and, where feasible, executable oracles (type-checker errors after a signature change; failing tests after a change; runtime traces). Communities used as task-complexity covariates are computed from the import graph only (an extractor-independent relation). · Avoids circularity between our graph and the labels it is scored against.
- **E3-D09** · Delegation: an external-research agent (literature, benchmarks, candidate repositories) and an Immich repository-analysis/bug-mining agent (Sonnet), both writing to `notes/`. Methodology and retrieval-architecture work stayed with the lead (full context of experiments 1–2). No two agents implement the same component.
- **E3-D10** · Task selection is method-independent. Candidates are excluded only for title-only reports, reports stating the fix mechanism, symptoms caused outside the analysed code, or unresolvable ground truth; difficulty strata (easy/medium/hard) are computed from lexical overlap, fix span and boundary type only. A retriever's rank (the mining agent's BM25 screen, its A/B/C tiers) is never used to include, exclude or tier tasks. · Choosing tasks on which one method fails biases the comparison against that method.
- **E3-D11** · Historical bugs are not automatically hard (Immich mining, `notes/immich-analysis.md` §3): BM25 put the fixed file in the top 10 for 78/97 candidates, and the median fix touches 1 file. The benchmark keeps the realistic mix, oversamples the hard stratum (≥ 50% cross-module), and reports every result by stratum. Twenty's reports come more often from maintainers' PR text (11/28 sampled server fixes link an issue), so its tasks need a leakage audit; a report is dropped, not rewritten, when no symptom-only text exists.

### Milestone 2 (owner authorisation 2026-11-09: non-billable implementation + retrieval-only stage 1; no agent stage)

- **E3-D12** · Regression gate for S before any extractor change. `scripts/exp3/regression-s.ts` rebuilds the base and 20 single-bug graphs in memory and compares with experiment 1's frozen hashes (`evaluation/results/graph-validation.json`): 21/21 identical before (`manifests/s-graph-regression-before.json`) and after (`…-after.json`) the M2.2 rules. Stage-1 S reproduces experiment 1's per-task metrics exactly for ripgrep, BM25, embeddings, custom_graph and hybrid, and `hybrid_nograph` equals the `no_graph_at_all` ablation on all 14 test tasks (`manifests/s-reproduction.json`).
- **E3-D13** · Opt-in `maxPackageDeclarationBytes` (graph builder and impact oracle): external packages whose declaration files exceed the limit are loaded as an untyped stub; the TypeScript library and `@types/*` are never stubbed; package identity is kept from the file path; stubbed packages are listed in coverage notes. Off by default (experiments 1–2 unchanged). Reason: Twenty's `googleapis` alone ships 189 MB of declarations (4.5× Twenty's source); a fully typed program plus walk needed > 6.5 GB.
- **E3-D14** · Generic M2.2 extraction rules (`src/parser/dispatch-extractor.ts`): (1) keyed dispatch — a handler registered by a method decorator carrying a typed key, a dispatch call carrying the same key; keys are enum members or literals only where the TYPE CHECKER's contextual/declared parameter type is that enum or named literal union (or `SomeClass.name`); handlers exclude route handlers and methods called directly from non-test code; each handler links through its most specific key; edges `framework_inferred`, confidence 0.8 (enum/class) / 0.7 (literal), evidence location kept; (2) GraphQL operations as route entry points (decorator package from the declaration, or from the import declaration when the package is stubbed); (3) Kysely table access as `QUERIES_DATABASE`. No repository names anywhere. Fixture tests cover 4 positive dispatch links, 6 negative cases, GraphQL and Kysely; S graphs unchanged (E3-D12). On the pinned snapshots: Immich 116 publish / 94 consume edges, 818 Kysely edges; Twenty 144 handlers, 105 keys, 183 producer edges, 716 GraphQL operations. Precision audit of sampled edges: see the stage-1 report.
- **E3-D15** · L graphs stub ALL third-party declarations (limit 0; workspace packages such as `twenty-shared`, `@types/*` and the TS library stay typed). Two fully typed Twenty builds were killed (OOM at 7.3 GB after 7 min; 6.5 GB after 14.5 min), so one build per task snapshot was infeasible on the 15 GB machine. Stubbed: 93 s, 4.0 GB, 100% of imports resolved, 19.3% of call sites unresolved (calls into libraries), TypeORM `QUERIES_DATABASE` edges lost (0). M keeps full typing (25 s, 1.9 GB, 0.08% unresolved). This is an unavoidable repository-level difference, reported with every L result. (Earlier M1 Twenty/Immich builds without their own `node_modules` had silently resolved NestJS/TypeORM from `targets/node_modules`, the experiment-1 dependencies; all M2 builds use each repository's own dependencies or stubs.)
- **E3-D16** · Category-A task pipeline (`scripts/exp3/tasks.ts`): bug snapshot = pinned snapshot with the fix's non-test TypeScript change reverted (`git apply -R`, exact or one line of fuzz); ground truth = declarations enclosing the changed lines on the bug side; candidates whose fix does not revert are not used (Immich 56/98 revert, Twenty 26/80). Fix patches contain upstream AGPL code and are kept outside the tracked tree (`targets/exp3/dataset-patches/`), reproducible from the recorded commit range and SHA-256. FAIL_TO_PASS is run in a copy of the snapshot (`targets/exp3/immich-ftp`): Immich 40 verified, 15 not runnable (database-backed tests only), 1 without a failing test. Category C direct impact comes from the type-checker oracle (`scripts/exp3/oracle-impact.ts`; edit applied in memory, importers type-checked): Immich 4/4, Twenty 3/3 tasks produced an impact set.
- **E3-D17** · Independent audits (separate Sonnet auditors; no retrieval output existed; the mining agents' BM25 screen was stripped from every file they used). - **E3-D18** · Embedding cache streamed and memoised per process, missing items embedded in batches of 5,000 (`src/retrieval/embeddings.ts`): Twenty's vector cache exceeds V8's maximum string length and was re-read by every method. Same keys and values (unit test); experiment-1 caches reused unchanged.
- **E3-D19** · Nested-corpus building blocks for L use a finer import-graph partition (Louvain resolution 8: 355 units, largest 43k lines) than the strata (resolution 1: 239 communities, largest 130k lines), chosen by a size rule (smallest resolution in {1, 2, 4, 8} whose largest unit is at most half the smallest target of ≈ 97k lines) before any L retrieval result existed. - **E3-D20** · Stage-1 method set: ripgrep, BM25, embeddings, hybrid_nograph, hybrid, custom_graph, compact_nograph, compact_graph (all frozen experiment-1 configurations; compact cap 800 tokens, 25 symbols, identical format). Graphify and CRG are not in the approved list for this stage.
- **E3-D21** · Keyed-dispatch precision fix after the independent edge audit (`dataset/audit/EDGE-AUDIT.md`), decided before any M/L retrieval result was read (the first Immich stage-1 run was stopped and deleted). First audit, 50 sampled edges per repository: GraphQL routes 15/15 and Kysely table edges 15/15 correct; dispatch pairs only 12/35 (Immich) and 11/35 (Twenty) — every job-name pair correct, errors from test files as producers, worker-filter and CRUD-action enums used as keys, OpenAPI documentation code, and handlers forwarding their own event. Three generic rules added: R1 producer sites in test files are ignored; R2 each handler links only through its most specific key domain (distinct registered values / registrations), and domains below 0.25 are broadcast/filter keys that never link; R3 a producer inside a handler of the same key is ignored. Fixture extended with each failure pattern; S graphs still 21/21 identical. Re-audit on fresh samples: see EDGE-AUDIT.md (v2).
- **E3-D22** · Literal dispatch keys typed as `keyof SomeMap` (Immich's event names) were never recognised: unions are interned, so the contextual type often lacks its alias. The key domain is now read from the DECLARED annotation of the position (property signature or parameter, type parameter -> constraint). Immich pinned graph: 156 handlers / 112 keys / 160 producer edges (was 64 job handlers only after E3-D21); Twenty: 100 handlers / 99 keys / 135 producer edges, 44 broadcast-only candidates (database-event actions) excluded.

- **E3-D30** · Root cause of the unexplained first-launch exit (E3-D28). `scripts/exp3/agent.ts` imported constants from `src/agent-eval/exp3/mcp-tool.ts`, and that module runs its own `main()` on import. Every agent runner therefore also started a stray stdio MCP server, which calls `process.exit(0)` when stdin closes. Launched from a shell whose stdin then closed, the runner exited 0 right after starting its daemon. Launched with `< /dev/null` (every launch that produced results), the stray server was harmless: no run's behaviour depends on it, and the agent's own MCP tool is a separate child process. The tool definition now lives in the side-effect-free `tool-def.ts` (byte-identical text); the runner and the packaged CLI import it from there.
- **E3-D31** · Retrieval head-to-head adapters (Amendment D2). Experiment 1's CRG adapter cloned *committed* history, so on M and L bug tasks (uncommitted reverted fix) it would have indexed the fixed code. graphify's adapter indexed the whole package directory, tests included. Both now index exactly the task snapshot's corpus files, from a fresh git repo at a neutral path (`neutralCopy`), the same files every other method indexes. The S competitor rows were recomputed this way, and the earlier S rows are kept locally as superseded; their means differed by at most 0.01. This was fixed after the first M attempt crashed, before any M or L competitor retrieval result existed.
- **E3-D32** · Amendment D2b result (same-embedder control). code-review-graph 2.4.0 with our Qwen3-Embedding-0.6B served through its own OpenAI-compatible provider (`code_review_graph_qwen`) scores symbol Recall@10 0.28 / 0.23 / 0.17 on S (20 tasks) / M (26) / L (18). Its default local embedder scores 0.31 / 0.26 / 0.10, and our `hybrid` scores 0.69 / 0.48 / 0.33. Paired hybrid − CRG+Qwen: +0.41 (16/0/4), +0.25 (13/1/12), +0.16 (11/1/6), all p < 0.01. The embedding model therefore does not explain the head-to-head gap: our embedder helps CRG only on L, and leaves it well below `hybrid` everywhere. Infrastructure fix found on the way: the helper embedding server kept `stage1.ts` alive after its last row (S finished, then hung for 72 minutes). The server is now unref'd, and `stage1.ts` exits explicitly once done. No rows were affected.
- **E3-D33** · Machine discipline. On 2026-11-15, running the agent queue, the SWE-bench runner, an ONNX check and a product smoke test at the same time exhausted the 15 GB of RAM. Everything was killed, and the M snapshot was left with its fix un-reverted. It was restored (`git checkout -- .`), every result file was checked intact, and all resumable runs resumed. Since then, all heavy work runs through one sequential queue (`experiments/run-queue.sh`): each step waits for 8 GB free and checks the snapshots are clean. On 2026-11-16 a build in another session filled memory during the M D2b step, so the queue was stopped by hand. The only loss was the M task in progress, which was recomputed. The queue now takes named steps, so the SWE-bench step (experiment 05) can be deferred.
